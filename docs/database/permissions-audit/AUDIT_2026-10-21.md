## Decision and principal findings

**Production release decision: BLOCKED.** The audit and isolated database tests support review of the correction. They do not authorize a hosted migration, merge, or release. No live database writes, privilege changes, Production reset, or historical-baseline replay against Production occurred.

The current migration chain already contains explicit grants for the application reads and writes examined. In particular, both tables created after the historical baseline explicitly grant their public reads, and both booking Remote Procedure Calls (RPCs) explicitly grant server execution. This is not evidence that existing application access has broken or will automatically break on October 30.

Three verified issues require action:

1. The historical snapshot restores broad default grants. A reconstruction can therefore appear compatible while silently restoring automatic exposure of later objects.
2. Existing hardening leaves unnecessary PostgreSQL 17 `MAINTAIN` privileges on 13 reference tables and browser permissions on 24 sequences. The two newer public-read tables also grant `service_role` broader access than current callers require.
3. The file in the active migration directory is explicitly an **evidence-only snapshot**, with numbered statements lacking terminal delimiters. Raw replay fails. A separately generated local adapter was necessary for testing; ordinary `supabase db reset` compatibility remains unverified.

These findings are supported by the [hosted catalog capture](evidence/hosted-catalogs-2026-10-21.json), [raw replay failure](evidence/raw-baseline-replay.log), [historical default-exposure probe](evidence/historical-default-exposure.log), and tests described below.

## What Supabase is changing

Supabase's [official announcement](https://github.com/orgs/supabase/discussions/45329) confirms the October 30 rollout to existing projects and the October 20 final notice. Existing table grants remain effective. Newly created or recreated `public` objects need the permissions required by their callers; `supabase-js` uses the Data Application Programming Interface (API), including the PostgREST access path. The supplied [Alleystreet notice](https://mail.google.com/mail/u/?authuser=admin%40alleystreet.com#all/1a1590deab200f38) is consistent with that announcement.

A PostgreSQL **role** is an identity under which database permissions are evaluated. A `GRANT` permits an operation on an object; **Row-Level Security (RLS)** determines which rows the role can access. Both matter. Removing RLS or introducing `SECURITY DEFINER` is not an appropriate response to a missing grant. A server's `service_role` bypasses RLS but still requires object privileges. See [Supabase's security model](https://supabase.com/docs/guides/api/securing-your-api) and [PostgreSQL row-security rules](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

`ALTER DEFAULT PRIVILEGES` affects subsequently created objects belonging to the specified creator role. It does not revise existing objects. Defaults are not inherited from the creator's other role memberships, and schema defaults add to global defaults. These details explain both the baseline replay trap and the correction's function scope. See [PostgreSQL default privileges](https://www.postgresql.org/docs/current/sql-alterdefaultprivileges.html).

## Application access and least-privilege decisions

The browser client in [`app/lib/supabase.ts`](../../../app/lib/supabase.ts) starts with the public API key. A signed-in user's JSON Web Token (JWT) makes database requests run as `authenticated`; a function named `makeAnonDb` does not imply that its JWT-authenticated requests run as `anon`.

| Application surface | Required access retained | Evidence |
|---|---|---|
| Approved location discovery and host lookup | `anon` and `authenticated`: `SELECT` on `approved_host_listings_public` | [`requests.ts`](../../../app/lib/requests.ts), [`location page`](../../../app/locations/[slug]/page.tsx) |
| Plain/pro terminology | Both browser roles: active glossary reads; signed-in user reads own profile default | [`TerminologyProvider.tsx`](../../../app/components/TerminologyProvider.tsx) |
| Booking creation and participant history | Authenticated request `SELECT, INSERT`; participant reads of messages/offers | [`requests.ts`](../../../app/lib/requests.ts) |
| Host submission and policy acknowledgment | Authenticated own-row `SELECT, INSERT`; administrative reads subject to existing policies | [`requests.ts`](../../../app/lib/requests.ts) |
| Approval and negotiation | Authorized server writes to source submissions/bookings/messages/offers; explicit service RPC execution | [`admin approval route`](../../../app/api/admin/host-submissions/update-status/route.ts), [`negotiation routes`](../../../app/api/negotiation/) |

The new projection and glossary tables require **no direct `service_role` grant for current callers**. Approval updates the source submission; the private synchronization function runs as its verified `postgres` owner and maintains the projection. Glossary seed/upsert SQL likewise runs as the migration owner. Direct service reads/writes to these two tables are therefore deliberately denied by the correction and tested as denied.

Reference, provider, workspace, and internal-record permissions remain aligned with the reviewed migration contracts even where no current page directly queries an object. This audit does not invent new browser write paths. Legacy broad service grants elsewhere are preserved because server workflows and administrative dependencies need a separate reduction review; this is not a claim that all historical privileges are minimal.

### Operations that need explicit handling in future work

Future public table creation, drop/recreate operations, new Preview environments, and clean database rebuilds must establish grants deliberately. Without them, public listing/glossary reads, authenticated inserts, or service data access can fail with PostgreSQL `42501`. Current public-read table migrations already contain their grants.

New public views and RPCs need their own reviewed permissions. Tables do not confer function execution or sequence access. For explicit `nextval` defaults, grant only the needed sequence `USAGE`; sequence `UPDATE` also permits counter reset. Current browser workflow inserts use Universally Unique Identifiers (UUIDs), and browser roles have no required sequence-writing path. The glossary identity sequence is owner-maintained. See [PostgreSQL sequence privileges](https://www.postgresql.org/docs/current/functions-sequence.html).

## Forward correction

[`20261021195905_explicit_public_data_api_permissions.sql`](../../../supabase/migrations/20261021195905_explicit_public_data_api_permissions.sql) was created with Supabase CLI `migration new`. It runs transactionally and:

1. Removes all public-schema defaults for `PUBLIC`, `anon`, `authenticated`, and `service_role` on future `postgres`-created tables, sequences, and functions. This prevents the baseline from leaving automatic exposure enabled.
2. Removes the global default `PUBLIC EXECUTE` for future functions created by `postgres`. **This applies in every schema, including future helpers outside `public`.** New migrations must explicitly grant required execution. Existing functions and other creators' defaults are unchanged; schema-scoped revocation alone cannot remove the global default.
3. Requires 15 expected `postgres`-owned, RLS-enabled tables and the owner-executed private projection helper before changing existing object grants. An unexpected target fails closed and rolls back the preceding default changes.
4. Reconciles the two new tables to browser `SELECT` only, removing unused service access and glossary sequence access.
5. Reconciles 13 reference tables to browser `SELECT` only, removing residual `MAINTAIN`, and removes browser privileges from the 23 legacy sequences. Together with the glossary sequence, 24 sequences are covered.

It adds no policies, disables no RLS, changes no object ownership, and leaves the existing service-only booking RPCs, authenticated booking inserts, provider column boundary, and participant/owner policies intact. The global future-function change is an intentional security contract, not merely an October 30 table-compatibility requirement.
